## 2. Design decisions that differ from the proposal

### 2.1 The refine backup (F5) — the result-inverting one

Eq. (2) is a zero-reward zero-discount backup. Implementing it as
`compute_target_q_dist(..., reward=0, discount=0)` gives `Tz = 0 + 0 * support = 0`, so
**every refine target collapses onto V = 0**. Then `W -> 0`, `Delta_r = W_child - Q^exec < 0`,
the rule never refines, and the depth histogram pins at 100% round 0 — which on a dashboard
is indistinguishable from *"the stopping rule works beautifully."*

Measured in T5: with `reward=0, discount=0` the projected target puts `1.0000` of its mass
within one atom of V = 0, `E[V] = 0` exactly, and total mass `2.000` (it is not even
normalised). `discount=1` is the other trap — every atom maps exactly onto an atom and the
default projection duplicates mass (measured `max |sum - 1| = 0.695`).

**Implemented instead:** the refine target *is* the child node's categorical distribution,
copied, bypassing the projection entirely.

The guard is logged every update. It is **not** `refine_target_mass == 1.0`, because the
leaf of the chain is the Bellman target, which carries the baseline's own documented C51
exact-atom duplication (`c51_exact_atom_fix: false`, kept deliberately so arm C stays
comparable to arm B). The correct invariant is
`1.0 <= refine_target_mass <= bellman_target_mass`, and both are logged. Observed live:
refine `1.0201` inside `[1.0, 1.0288]`. As a bonus, the position within that interval is
informative — it says roughly what fraction of refine targets took the *exec* branch of
`W_r = max(Q^exec_r, W_{r+1})`.

### 2.2 `u_r` without a double-Q

§3.3 defines `u_r = |Q_A - Q_B|` from clipped double-Q. This codebase has one critic
(`self.critic` + `self.critic_target`). Adding a twin would change the baseline's optimism
profile and destroy the "everything else identical" claim. Implemented instead:
`u_r = sqrt(sum_i p_i (z_i - Q)^2)`, the C51 spread of the node's own distribution
(`zoomq.uncertainty=c51_std`). `target_gap = |Q_online - Q_target|` is implemented as the
ablation alternative. **§3.3 of the paper needs a one-line note that the yardstick differs
from the draft.**

### 2.3 Training the exec heads without touching the replay schema

`Q^exec_r` may only be trained on transitions where the executed action *was* the round-r
skeleton. Rather than store the executed depth (a replay-schema change), the code measures
it: a chunk qualifies at round r iff its dyadic reconstruction RMSE is within
`exec_match_tol` (0.05). This is exact for online rollouts — by T2's nestedness, an action
executed at depth r0 is bit-identically the round-r skeleton for **every** `r >= r0` — and
it is the natural relabelling criterion for demos.

That predicate is what the `exec_n_r` counter reports, and it produced the night's
cleanest correctness check. Gate 0, written independently as a numpy script by a separate
agent that never saw this code, predicted `exec_n_r = [0.6273, 0.8638, 0.8734, 0.8817,
1.0000]`; the live training run logged `[0.628, 0.861, 0.867, 0.875, 1.000]`. Two
independent implementations of the dyadic projection agree to <= 0.007 at every round.

### 2.4 Stopping rule at act time

§3.3's `Delta_r = W_{r+1} - Q^exec_r` needs the child's value, which is only knowable by
computing it. Implemented as a one-step lookahead: descend to round r+1, then stop when
`Q^exec_{r+1} - Q^exec_r <= kappa * u_r`. The executed depth is the deepest round computed.
This is the honest practical instantiation of `W_r = max(Q^exec_r, max_child W_{r+1})`, and
it is what `depth_share_r` counts.

### 3.2 The action space is task-specific — Gate 0 must be re-run per task

`drawer_top_close` has a **16-dimensional** action, not `move_plate`'s 15, and it has **two**
dead dimensions (14 and 15, both constant -1.0) rather than one. It also has **no binary
dimension at all** — nothing has fewer than four distinct values, so `move_plate`'s gripper
(dim 13) has no counterpart here.

Three consequences:

- `cfgs/config_zoomq_bigym_gate0.yaml` correctly **refuses** to load on this task —
  `ZoomQCritic` raises when a `w_schedule` row length does not match the action dim. The
  guard works, and it is the reason the calibrated windows were never silently misapplied.
- `zoomq.hold_dims=[13]` is a `move_plate`-specific setting. A `drawer_top_close` arm using
  it was considered and **not launched**: there is no binary slot to hold.
- Arm G's `window_clamp_rate` of 0.0845 is therefore not just "windows calibrated on the
  wrong task" — it is windows calibrated on a **different action space**. Gate 0 is a
  per-task procedure, not a one-off.

## 4. Gates

### Gate 0 — residual calibration (`gates/gate0_*`) — **DONE, and it contradicts the proposal**

Data: 7,709 non-padded 16-step chunks from the 54 successful `move_plate` demos, read from
`runs/A/demo_buffer/` — i.e. in exactly the normalised action space the critic sees. The
script's dyadic schedule was verified identical to `bigym_src/zoomq.py`'s to float32
precision, and its DP was verified against brute force.

**The proposal's windows are too narrow at every round**, by 1.5x-3.9x:

| round | proposal `w` | measured `1.5 * p99` | ratio |
|---|---|---|---|
| 1 | 0.15 | **0.5794** | 3.86x |
| 2 | 0.08 | **0.1624** | 2.03x |
| 3 | 0.04 | **0.0596** | 1.49x |
| 4 | 0.02 | **0.0395** | 1.97x |

**Root cause: action dimension 13 is a *binary* gripper taking only `{-1, +1}`** (exactly 2
distinct values across all chunks; every other dim has >8,000). When it toggles inside a
chunk — 12.53% of chunks — its interpolation residual reaches **1.0667, larger than the
action range**, so no window inside `[-1, 1]` can contain it. Dimension 14 is dead
(constant `-1.0`). A single scalar per round is therefore set by the gripper and runs the
13 continuous dims 2-4x wider than their own data needs, wasting bin resolution at the
coarsest and highest-leverage round.

This is why `w_schedule` now accepts **per-(round, dimension)** rows
(`cfgs/config_zoomq_bigym_gate0.yaml`, arms D2/E2). It halves the pooled clamp rate
(0.00478 -> 0.00232) and flattens the continuous dims into a 0.000-0.007 band. The residual
4.9% gripper clamping at round 1 is irreducible by window tuning.

**`j*`:** measured `j* = 3` by both the dyadic schedule and optimal-DP knot placement
(mean RMSE <= 0.05). The proposal's `j* = 4` is not even a member of the dyadic schedule
(sizes are 2, 3, 5, 9, 16). At exactly four knots, measured RMSE is 0.0215 (uniform) /
0.0074 (optimal DP) against the proposal's stated 0.0252.

**Cost of the fixed schedule:** dyadic minus optimal-DP mean RMSE is +0.0084 at j=3,
**+0.0129 at j=5** (3.7x the optimal error), +0.0086 at j=9. The fixed dyadic placement is
a real, quantified tax.

**Smoothness:** all reconstructions sit inside the demos' own `|da|` / `|d2a|` envelope at
every j — they are strictly smoother, never jerkier.

### Gate 1 — skeleton replay (`gates/gate1_*`) — **PASS**, and it explains Open Item 1

**Verdict: PASS.** `j = 3` (knots at t = 0, 7, 15) scores **0.817** against the `j = 16`
control's **0.750** — 109% of the control, far above the pre-registered 90% bar. The depth
floor sits between 2 and 3 knots.

Success vs j (n = 60 demos per cell, binomial se ≈ 0.056):

| j | 2 | 3 | 5 | 9 | 16 |
|---|---|---|---|---|---|
| success | 0.467 | **0.817** | 0.767 | 0.733 | 0.750 |
| % of j=16 | 62% | 109% | 102% | 98% | 100% |

`j = 16` reproduces the raw-replay number exactly, so the projection path is clean. j ∈
{3, 5, 9} are all within ~1.2 se of the control; only j = 2 is genuinely below it (3.6 se).

Per-chunk end-effector deviation (426 chunks, bit-exact-ish state restore at each chunk
start): j=2 17.4 mm, j=3 5.6 mm, j=5 1.6 mm, j=9 0.6 mm, j=16 0.0 mm. Deviation peaks
**mid-episode** (reach / transport), not at contact — which is why this is PASS and not the
GRADED outcome the plan considered most likely.

Controls: replacing linear interpolation with a **zero-order hold** costs 0.35 success at
j=2 and 0.23 at j=3 and nothing at j >= 5 — so at the coarse end it is the linear segments,
not merely the knot count, doing the work. Perturbing one knot by one *fine bin* (0.016)
costs 0.12; perturbing it by one *residual-window quantum* (0.15) destroys the task
(0.083 at j=3). A knot has to be resolved well inside its window.

**Three caveats a reader needs.**

1. **The PASS is measured on the `floating` substrate, not the production HOMIE env** — for
   the reason in Open Item 1: the production env replays its own demos at **0 / 60**, so
   the sweep there is flat 0.000 at every j *including the identity j = 16*, and nothing in
   it is interpretable. This gate therefore tested the arm/gripper trajectory in isolation
   from the locomotion controller. Re-running it on native HOMIE demos (recorded with
   `homie_cmd` and a >= 1 s success tail) is the one experiment that could turn PASS into
   VETO.
2. **State restore is *not* bit-exact on this scene**, contrary to
   `tests/smoke/snapshot_roundtrip_probe.py`'s GOLDEN record — that was measured on a
   walking sequence with no object manipulation. Only ~19% of chunk restores are exactly 0;
   worst-case wrist reproduction is 5.7e-5 m. That is 300x below the j=2 signal and 10x
   below j=9, so the table holds, but the harness must not be pushed finer than j = 9
   without re-deriving the floor.
3. Demos replay under MuJoCo 3.11.0 though recorded under 3.1.5. The 0.750 ceiling at
   j = 16 (rather than 1.0) is that version drift, not a harness bug.

### Gate 2 — **not deferred any more: it fails, for an identified reason**

The plan expected Gate 2 to be undecidable tonight because online return would be
identically zero. That expectation was half right. On `move_plate` return *is* zero. But
arm G on `drawer_top_close` reaches eval reward 1.000 and carries a real value estimate
(`Q^exec = 0.397`), and there the rule still never refines: the execution heads read the
same value at every depth to three decimals, so `Delta_r = 0`.

So the honest verdict is not "insufficient signal". It is that **the stopping rule cannot
fire under the current exec-head training scheme**, and §5.1 shows why it is structural
rather than a matter of more steps. Arms D vs E remain uninformative as a *contrast* — E
sits at 100% round 0 and D's spread is entirely its own forced exploration — but that is
now a diagnosis rather than a missing measurement. Gate 2 should be re-run after one of
§5.1's three fixes lands, not after more training.

## 5. Where I got stuck, and the assumptions I made

### 5.1 Why the stopping rule never refines — the mask is the cause

Every ZoomQ arm ends the night with `Q^exec_r` **identical across depths to three decimal
places**. Arm G, which actually solves its task and carries a genuine value estimate:

| arm | eval R | `exec_q` at depths 0..4 | `depth_share` 0..4 |
|---|---|---|---|
| G | **1.000** | 0.397 / 0.396 / 0.396 / 0.396 / 0.396 | 0.865 / 0.038 / 0.031 / 0.036 / 0.029 |
| D | — | 0.236 / 0.236 / 0.236 / 0.236 / 0.236 | 0.870 / 0.032 / 0.036 / 0.040 / 0.022 |
| E (`eps=0`) | — | 0.251 / 0.251 / 0.251 / 0.251 / 0.251 | **1.000** / 0 / 0 / 0 / 0 |

With `Q^exec_{r+1} - Q^exec_r = 0` the rule `refine iff Delta_r > kappa*u_r` can never fire,
so arm E — the pure rule with no exploration — executes at round 0 on **100%** of rollouts.
D's ~13% spread away from round 0 is accounted for by its `eps_depth` forcing rather than by
the rule: `eps` anneals 0.30 -> 0.05 over the run and a forced draw is uniform over five
depths, giving `mean(eps) * 4/5` ~ 0.10-0.13 against the 0.130 observed. Arm E is the clean
statement, because it has no forcing at all: **the rule refines on zero rollouts.**

**This is not the F5 trap** (`refine_target_mass` sits inside `[1.0, bellman_target_mass]`
on every arm) **and not the absence of reward** (arm G solves its task). It is structural,
and the cause is the shortcut in §2.3.

`exec_valid_r` marks a stored chunk as a training label for depth r when the chunk *is* the
round-r skeleton within tolerance. But by nestedness (T2), a chunk representable at round r
is representable at **every deeper round**, and all of those skeletons are the *same action*
— so they earn the *same return*. Every head that receives a sample therefore receives the
same target as every deeper head. **The mask that makes the backup unbiased is exactly the
mask that deletes every sample in which a coarse skeleton would have been worse.**

The counters show it directly: `exec_n = [0.55, 0.76, 0.79, 0.82, 1.00]` on arm D. 55% of
the batch is a "valid" label for depth 0, and for all of it the round-0 skeleton reproduces
the executed action — i.e. the round-0 head is being taught, over and over, that coarse
execution is free.

`eps_depth` was meant to supply the missing counterfactuals, and it does supply some: a
forced depth-r rollout stores a genuinely coarse action. But at `eps` annealing 0.30 -> 0.05
spread over five depths those samples are ~1-6% of the batch, against the ~55% of "free"
samples pulling the other way — and by nestedness they *also* feed every deeper head, which
keeps the heads tied together rather than separating them.

Three fixes, in increasing order of cost:

1. **Train head r only at the MINIMAL round at which the chunk is representable**, not at
   every round at or beyond it. No replay-schema change, a few lines. It breaks the tie
   immediately, at the price of training each head on a biased (harder) subset.
   **Implemented and unit-tested tonight** as `zoomq.exec_match_mode=minimal` (default stays
   `any`, so nothing running was disturbed). Probe T12 both verifies it and measures the
   defect: on a mixed batch the valid set is the upward-closed suffix nestedness predicts
   (per-round label counts `[0, 16, 16, 16, 32]`), and the default mode issues **80 labels
   where `minimal` issues 32** — 60% of the training signal is duplicate targets whose only
   effect is to hold the heads together. Launch it as
   `--config-name=config_zoomq_bigym zoomq.exec_match_mode=minimal`. **It was run as arm M
   and it FAILED** — see the verdict below. Keep the flag for the record; do not use it.

   **VERDICT ON FIX 1: it separates the heads, and the separation is spurious. Do not
   ship it.** Arm M ran 7,093 frames. Three things happened, in order of importance:

   | | `exec_q` at depths 0..4 | spread | eval R |
   |---|---|---|---|
   | G (`any`, 18,279 frames) | 0.3395 / 0.3395 / 0.3394 / 0.3394 / 0.3395 | 0.00018 | **1.00** |
   | M (`minimal`, 7,093 frames) | 0.4560 / 0.4468 / 0.4199 / 0.4130 / 0.4096 | **0.0464** | **0.00** |

   1. **The tie is broken — 258x more spread.** `exec_n` now sums to 1.00 instead of 4.60,
      the heads train on disjoint data, and they diverge. The diagnosis in this section is
      confirmed: the mask was the cause.
   2. **But the ordering is inverted.** `Q^exec` *decreases* monotonically with depth, so
      the coarsest skeleton is scored as the most valuable and `Delta_r < 0` everywhere —
      the rule is now pushed toward stopping early *harder* than before. This is exactly
      the bias predicted above, and now measured: `minimal` attributes each sample to the
      coarsest round that reproduces it, so head 0 is trained on the smoothest, easiest
      chunks and head 4 on the residue that nothing coarse could represent. **The heads are
      separating by sample difficulty, not by execution quality.** Stable from frame 3,793
      onward, so it is not a transient.
   3. **And it costs the task.** M reads `R=0.00` at both evaluations (frames 2,630 and
      5,293) where G had already reached `R=1.00` by frame 5,122.

   So fix 1 does what it was designed to do and is still the wrong fix. Only the executed
   depth identifies which head a return belongs to, and no function of the stored chunk
   alone can recover it — precisely because nestedness makes the chunk consistent with every
   depth at or beyond its own.

2. **Attribute by executed depth** — `zoomq.exec_match_mode=online_minimal`, **implemented
   after M failed and now running as arm N**. It gets option 2's semantics without touching
   the replay schema, by noticing that the two sample sources need opposite treatment:

   - **Online rollouts have an executed depth, and the minimal rule recovers it exactly.**
     A rollout forced to depth r stores the round-r skeleton, and exploration noise
     (sigma 0.01) stays well inside `exec_match_tol` (0.05), so its coarsest representable
     round *is* r.
   - **Demonstrations have no executed depth at all** — the policy never executed them. A
     demo chunk is a full-resolution action, so it labels the deepest head only.

   That is precisely what fix 1 got wrong: demos dominate the batch, so attributing *them*
   by representability is what sorted the heads by chunk smoothness. Probe T12 measures the
   change: demo rows contribute **16 labels to the coarse heads under `minimal`, 0 under
   `online_minimal`**. The coarse heads are then trained only on rollouts actually executed
   at their depth — sparse (they depend entirely on `eps_depth` forcing) but correct, and
   `exec_n_r` reports exactly how sparse.

3. **The replay-schema version remains the belt-and-braces option** if N's coarse heads turn
   out too starved: one `int8` field carrying the executed depth removes the reliance on the
   noise-vs-tolerance margin above.
2. **Store the executed depth in the replay buffer** and train head r strictly on
   depth-r-executed transitions. This is the semantically correct version and the one the
   proposal implicitly assumes; it is the replay-schema change §2.3 set out to avoid, and
   avoiding it is what caused this.
4. **Raise `eps_depth` substantially, or importance-weight forced-depth samples**, so the
   counterfactuals are not swamped. Cheapest to try, weakest guarantee; complementary to 2.

Until one of these lands, **no run can produce a non-trivial depth histogram**, and Gate 2
cannot be settled by any amount of additional training.

### 5.2 Cross-round coordination rides the anchor, not the recurrence

§3.2 motivates the dyadic decision order with a sequential chain: a knot's decision is
conditioned on every knot committed before it, which a marginal-independent argmax cannot
represent. **That is only half true as implemented, and the half that fails is the half the
proposal leans on.**

Information about an already-committed knot can reach a later decision by two routes:

1. the **residual window's anchor** `p_j`, which is built from committed *final* values, and
2. the **GRU**, whose per-position input is that position's own level-`l` interval midpoint.

Route 2 carries nothing at level 0, because at level 0 every position's midpoint is just
its window centre — independent of any bin anyone will choose. So at the coarsest amplitude
level, the recurrence is blind, and coordination is entirely route 1.

T10 measures this with a two-mode joint whose marginals are uninformative, asking a
*conditional* question (pin `a_0 = +0.6` vs `-0.6`, read the preferred bin for `t = 7`):

| | result |
|---|---|
| (a) anchor **open** (`p_7 = a_0`) | bin **4** vs bin **0** — a maximal flip. §3.1's window mechanism works, decisively. |
| (b) anchor **closed** (`p_7 = 0` in both modes) | bin **1** vs bin **1** — the level-0 recurrence carries nothing. |
| (c) same-round pair (`t=0`, `t=15`), level 0 | identical — within a round, ZoomQ is exactly as parallel as CQN-AS. |

Closing the anchor exactly matters and is easy to get wrong: `t = 7` sits at interpolation
weight 7/15 along `[0, 15]`, **not** at the midpoint, so the obvious construction
`a_15 = -a_0` leaves `p_7 = a_0/15` — a small anchor leak that made an earlier version of
this test read a spurious `1.0e-03` response. Solving `p_7 = 0` exactly gives the clean
result below.

Measured as a *representational* property (perturb `a_0`, read `|dQ(t=7)|` at level 0), not
as a learned one — "did not learn it" would not distinguish "cannot represent it":

| `cond_mode` | level-0 `|dQ(t=7)|` w.r.t. `a_0`, anchor closed |
|---|---|
| `midpoint` (default, all arms A-H, D2, E2) | **0.000e+00** — provably blind |
| `final` (the fix, arm D3) | **2.523e-03** |

So ZoomQ's coordination gain over CQN-AS is real, but it comes from the *anchored window*,
not from the sequence model. And two knots committed in the **same** round — including
round 0, which commits both endpoints — are as uncoordinated as in CQN-AS.

**The fix is implemented, unit-tested, and now running as arm D3:**
`zoomq.cond_mode=final` re-feeds earlier rounds at their committed final values through a
second prefix pass per round (still O(T) recurrent steps per level, about 2x the work).
The default stays `midpoint`, so every arm launched before it is unaffected.

### 5.3 Assumptions I made without being able to check them

- **`exec_match_tol = 0.05`** is a judgement call. It has to exceed the training-time
  exploration noise (`stddev_schedule = 0.01`) and admit demo chunks at `n_r >= j*`. Gate 0
  independently landed `j* = 3` at exactly this threshold, so the choice is consistent, but
  it was not derived.
- **The exec head reads level `L-1` features**, so it sees the skeleton at one-level-coarser
  amplitude than the executed action. The gap is `window / bins^2` (about 0.006 at
  `w = 0.15`), which I judged negligible against keeping training cost identical to CQN-AS.
  Not measured.
- **Teacher-forcing convention.** In training, a knot's window is anchored on the *true*
  action's neighbours; at inference it is anchored on the policy's own committed values.
  This is the standard autoregressive exposure mismatch and I did not attempt to correct it.
- **`kappa = 1.0`** is the paper's default and was not tuned.

### 5.4 Three instrumentation faults found by watching the runs, not by testing

- **Evaluation cost more wall clock than the training it interleaved.** At
  `eval_every_frames=2500` with `num_eval_episodes=10`, an eval is 3,000 environment
  steps — and on this task episodes *never* terminate early, so it always pays the full
  300-step timeout ten times. Measured duty cycle: ~42 min of training then ~50 min of
  evaluation, i.e. **46% of the night would have gone into producing rows of 0.0 that
  Gate 1 had already proven uninformative**. The seven arms whose deliverable is the
  mechanism counters were restarted with `EVAL_EVERY=25000`; A, H and the floating arms
  I/I2/J keep the normal cadence because their eval numbers are the point.
- **`depth_share_r` was counting evaluation acts.** `eps_depth` is disabled during eval by
  design, so eval acts all land at the adaptive depth and dilute the histogram with a
  different policy's decisions. Now counted from training rollouts only. Eval-time depth is
  deliberately *not* logged separately: `logger.py` freezes the CSV fieldnames at the first
  dump and these runs resume from snapshots, so the key set must never grow mid-run.
- **`save_snapshot` pickles whole modules, so adding a buffer breaks resume.** Snapshots
  written before tonight's per-dim windows and `hold_dims` lacked those buffers, and every
  resumed ZoomQ arm died in `act()` with an `AttributeError`. Fixed with a `__setstate__`
  that re-derives the schedule buffers — all of them are pure functions of the schedule and
  hold no learned state, so the rebuild is exact. **This will bite again**: any future
  buffer added to `ZoomQCritic` must be handled there, or every existing snapshot becomes
  unloadable.

### 5.5 Things that cost time

- Fork `main` is ahead of ali's pinned bigym (§1). Every arm crashed at env construction
  until the compat shim landed.
- Hydra rejects `--config-name` after positional overrides, so the launcher needed it as an
  explicit argument.
- `envsetup.sh` exits non-zero, so `set -e` in the launcher killed every run silently, with
  a zero-byte log.

## 6. What to do next, ranked by value

1. **Move the whole programme onto a substrate where the demos execute.** Open Item 1 is
   now resolved, not merely suspected: the production config replays its own demos at 0/60,
   for two independent reasons. Every HOMIE-era arm in this repo — including the completed
   100K-frame baseline — has been measuring a task no policy can score on. Either fix
   `success_hold_seconds` **and** the HOMIE pelvis tracking, or run on the floating
   substrate (arms I/J started tonight). Nothing else on this list matters until this does.
2. **Watch arm N (`exec_match_mode=online_minimal`) — this is the live test of the fix.**
   Highest-value algorithmic item, and it blocks Gate 2 entirely: as built, `Q^exec_r` is identical at
   every depth on every arm, so the stopping rule provably cannot fire however long anything
   trains. **Do not bother with the cheaper minimal-round heuristic — it was run tonight as
   arm M and it failed**: it separates the heads (258x more spread) but by *sample
   difficulty* rather than execution quality, inverting the ordering so coarse depths score
   *higher*, and it drove eval reward to 0.00 where the control had reached 1.00. Only the
   executed depth identifies which head a return belongs to, and no function of the stored
   chunk alone can recover it — nestedness makes the chunk consistent with every depth at or
   beyond its own. N gets that semantics without a schema change by treating online
   rollouts and demonstrations oppositely (§5.1, option 2). Check `exec_q_0..4` on N: they
   should separate **and increase with depth**, the opposite of M. If the coarse heads are
   too starved, add the `int8` executed-depth field to the replay schema.
3. **Get a proper baseline comparison before any claim of benefit.** Arm K shows CQN-AS
   matching or beating ZoomQ on `drawer_top_close`, on two eval points. Before the paper
   claims anything, run both arms to convergence on 2-3 tasks with multiple seeds. As of
   tonight the honest position is parity, on one easy task, n=1 seed.
4. **Promote `cond_mode=final` from arm D3 to the default if it holds up.** §5.2 shows the
   proposal's central architectural claim is only half-realised; the fix is written,
   unit-tested and running. Its clamp rate is already the lowest of the ZoomQ arms
   (0.0208 vs D's 0.0358) and its depth histogram is the least pinned (0.832 vs 0.870).
5. **Give the gripper a discrete head.** Dimension 13 is binary; refining it through a
   continuous residual window is meaningless, and it alone caps `exec_n_r` near 0.88 at
   rounds 1-3 no matter how good the policy gets. A wider window does not help — Gate 0 is
   explicit that this is a projection limit, not a tuning one.
6. **Reconsider round 0.** It commits both endpoints simultaneously and therefore cannot
   coordinate them (§5.1c). Splitting it into two rounds of one knot each would cost one
   extra round and fix it — at the price of changing the `n_r` sequence quoted in the paper.
7. **Re-derive §4's calibration numbers.** Gate 0 disagrees with the proposal on `w_r` (all
   four rounds), on `j*` (3, not 4), and on the four-knot RMSE. `j* = 4` is not a member of
   the dyadic schedule at all.
8. Ablate `uncertainty=target_gap` against `c51_std`, and sweep `kappa`. Both are wired.

### Open Item 1 — **RESOLVED**: the production env cannot replay its own demos

This started the night as "we suspect an era mismatch". Gate 1 settled it with a direct
experiment, and the answer is not the one we assumed. **The stock `move_plate` demos replay
at 0/60 in the production config.** Two independent causes, neither of which the other
rescues:

| variant | raw-replay success (n=60) |
|---|---|
| **`homie` production (`hold=1.0`, `z=0.92`)** | **0.000** |
| `homie`, `hold=0`, `z=0.92` | 0.017 |
| `homie`, `hold=1.0`, `z=1.00` | 0.000 |
| `homie`, `hold=0`, `z=1.00` | 0.000 |
| `homie`, `hold=0`, `reset_warmup_steps=0` | 0.067 |
| `homie`, `hold=0`, `cmd_clip=5` | 0.100 |
| **`floating` (the demo recording era), `hold=0`** | **0.750** |

**Cause A — `success_hold_seconds=1.0` is structurally unsatisfiable on these demos.** It
compiles to 50 consecutive control steps, but the stock demos carry a mean of 20.3 steps
after their first rewarding step, a maximum of 26 across all 60, and 9 have none at all.
**0 of 60 demos are long enough to satisfy it.** Flipping only this setting takes the
working substrate from 0.750 to 0.000. No policy — trained or perfect — can score above
zero here.

**Cause B — the HOMIE base loses the pelvis.** It is already **4.7 cm** off the demo pelvis
*at reset, before any action is taken*, and drifts to **20 cm** by demo end, versus 1.3 cm
for the kinematic floating base. That alone takes 0.750 to 0.017.

So the completed 100K-frame run's flat 0.0 is fully explained without invoking the
algorithm, and arm H's single-variable probe (`success_hold_seconds=0`) was necessary but
provably not sufficient — it addresses A and leaves B.

**Acted on tonight:** arms **I** (ZoomQ) and **J** (matched CQN-AS control) were launched on
the `floating` substrate with `success_hold_seconds=0` — i.e. the one configuration in
which the demonstrations are actually executable. They are the only arms in the programme
where a non-zero online return, and therefore Gate 2, is reachable.

### Open Item 3 — the baseline's C51 exact-atom bug gets *worse* as training converges

`c51_exact_atom_fix: false` is the repo default and duplicates target mass whenever the
Bellman image lands exactly on an atom. In a zero-reward world `Tz = gamma^K * z` puts the
support point `z = 0` exactly on the centre atom for every sample, so the duplication is
guaranteed — and it *grows* as the value distribution concentrates there. Measured on arm D:
`bellman_target_mass` went `1.0288` (900 frames) -> `1.0917` (1200 frames), i.e. the
critic's regression target is ~9% over-normalised and climbing.

This is a property of the **baseline**, not of ZoomQ — arm B has it too, it simply does not
log it. ZoomQ inherits it deliberately (so arm C stays comparable to arm B) and reports it.
Worth deciding explicitly before any paper table is produced.
