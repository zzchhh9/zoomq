## 0. 一句话

ZoomQ 写出来了、跑起来了、能解任务；但它的**核心卖点——那个"什么时候可以少算一点"的
停止规则——在原始设计下从数学上就不可能触发**。我找到了原因，试了三种修法，第三种把方向
掰对了。另外，顺手证明了你那个跑了 100K 帧、成绩全 0 的 baseline **不是算法的问题**——
那个任务配置下，连人类专家的完美示范原样重放都是 0 分。

## 1. 先说清楚 ZoomQ 想干什么

机器人每次决策不是输出"下一步动作"，而是输出**一整段 16 步的动作序列**（叫 chunk）。
原来的做法（CQN-AS）是：16 个时刻的动作，一次性全部定下来。

ZoomQ 的想法像**画草图**：

```
第 0 轮：只定首尾两点        ●─────────────────●     中间全靠直线连
第 1 轮：加中间那点          ●────────●────────●
第 2 轮：再加两点            ●───●────●────●───●
第 3 轮：再加四点            ●─●─●─●─●─●─●─●─●
第 4 轮：补齐全部 16 点      ●●●●●●●●●●●●●●●●
```

关键在于：**每一轮画完都已经是一条完整、可以直接执行的轨迹**（没画的点用直线补上）。
所以理论上可以"随时停笔交稿"——简单的动作画两笔就够了，难的才画满。省下来的计算就是卖点。

配套还有两个设计：

- **残差窗口**：第 1 轮之后，每个新点其实离"两个邻居连线的中点"不远。所以不用在整个
  `[-1, 1]` 范围里搜，只在中点附近一个小窗口里搜就行。同样的格点数，精度高 7–50 倍。
- **停止规则**：什么时候停笔？如果"再画一轮"带来的价值提升 `Δ`，超过了这个估计本身的
  不确定度 `u`，就继续画；否则停。

我今晚就是把这套东西实现出来，然后看它到底成不成立。

## 2. 我做了什么

### 2.1 三层仓库

| 层 | 位置 | 内容 |
|---|---|---|
| 论文 | `~/anchor_q` | 今晚没碰 |
| 算法 | `zzchhh9/CQN-AS-G1` 分支 `zoomq`（作为 submodule）| `bigym_src/zoomq.py` + 配置 |
| 实验 | `zzchhh9/zoomq`（伞仓库）| 关卡、脚本、报告 |

这么分层是有目的的：**算法改动必须小到可以"用 diff 当证据"**。
`git diff fba52f7..zoomq --stat` = 6 个文件、+2150 行，其中训练脚本只动了 **+8 行**
（两行 `hasattr` 保护的钩子，对原版 agent 完全无效）。这样"除了 ZoomQ 本身，其他一切都
没变"这句话是可以直接验证的，不用信我。

### 2.2 算法实现的思路

好消息是这个代码库比想象中更适配：它的 critic 本来就有一个沿"chunk 内 16 个时刻"跑的
GRU、共享的输出头、以及逐 (时刻, 维度) 的区间上下界。所以改动可以概括成一句话：

> **把 GRU 的序列轴从"时间顺序"换成"决策顺序"，并把每个位置的条件输入从"上一层的区间中点"
> 换成"当前草图在该点的预测值"。**

再加一个第二输出头（估计"在第 r 轮停下来值多少分"）和两类 backup。
`ZoomQAgent` 直接 subclass 原来的 `CQNASAgent`，所以 diff 才能这么小。

### 2.3 测试（67 项，全过）

不跑仿真、纯 CPU、秒级。挑几个重要的：

- **嵌套性**：一条已经是"第 r 轮草图"的轨迹，再投影到任何更深的轮次，必须**逐位相同**。
  实测 `1.19e-07`。这条是后面一切的基础（也是后面出问题的根源，见 §3.1）。
- **F5 陷阱**：一个会让结论完全反过来的坑，见 §5.1。
- **两模式玩具**：论文 §3.2 的核心架构主张，实测发现只对了一半，见 §3.5。

其中两项测试**在烧任何算力之前就抓出了真 bug**，最典型的是 softmax 轴写错了：原代码写
`softmax(q_logits, 3)`，那是因为它先把某个轴索引掉了；我的版本保留了那个轴，于是 3 号轴
变成了另一个东西，概率归一化到了错误的维度上——**不会报错，只会静默算错**。

## 3. 发现了什么

### 3.1 【最重要】停止规则永远不会说"继续"，而且这是必然的

**现象**：十条 ZoomQ arm 上，"在第 r 轮停下来值多少分"这个估值 `Q^exec_r`，
**在所有深度上三位小数完全一样**。包括 arm G——它真的解决了任务、critic 有真实的价值估计：

```
arm G:  0.3156  0.3157  0.3157  0.3156  0.3157      跨深度差异 = 0.0001
```

既然所有深度值都一样，`Δ = 0`，那"Δ 是否大于不确定度"这个判断**永远是否**，规则永远停在
第 0 轮。ε 强制探索之外，它一次都没主动选择过"继续细化"。

**这不是 bug，也不是没有奖励信号**（G 解决了任务）。它是设计本身导致的，原因很值得记住：

我要训练"第 r 轮停下来值多少分"，就得给它样本。我用的判据是：

> 这条存下来的轨迹，是不是就等于它的"第 r 轮草图版本"？是的话，就拿它的实际得分来训练。

问题出在**嵌套性**上——就是测试里那条 `1.19e-07`：

> 如果一条轨迹能被第 r 轮的草图表示，那它**必然**也能被所有更深的轮次表示，
> 而且**它们是同一条轨迹、拿到同一个分数**。

所以每一个深度的估值头，拿到的训练目标**完全一样**。它们当然估出一样的值。

**换个说法**：我为了保证"训练无偏"而设的那个筛选条件，恰好把所有"画得粗会出事"的例子
**全部筛掉了**。估值头从来没见过一个"偷懒结果变差"的样本——因为真正会变差的那些粗草图，
根本就没被执行过，也就没有分数可学。它自然学不会什么时候不该偷懒。

数字上看得很清楚：arm D 的 `exec_n = [0.55, 0.76, 0.79, 0.82, 1.00]`——
**55% 的 batch 在教第 0 轮的估值头"画两笔就够了，不花钱"**。

> **可以带走的通用教训**：只要你想让某个估值器给"降级版本"打分，而你用来筛样本的条件是
> "降级版本能复现实际执行的东西"，那你筛出来的**恰好是没有降级的那些情况**。
> "变差"的样本必须刻意制造，不会自己出现。

### 3.2 修法试了三种，第三种方向才对

| 归属规则 | 想法 | `exec_q` 深度 0→4 | 结果 |
|---|---|---|---|
| `any`（原始）| 所有能表示它的轮次都算 | 0.3156 / 0.3157 / 0.3157 / 0.3156 / 0.3157 | **完全不分开** |
| `minimal` | 只算最粗的那一轮 | 0.4410 / 0.4336 / 0.4046 / 0.3975 / 0.3943 | 分开了，但**方向反了** |
| `online_minimal` | 见下 | **0.3660 / 0.4446 / 0.4895 / 0.4993 / 0.5323** | 分开了，**方向对了** |

**第二种（`minimal`）为什么反了**：它把每条轨迹归给"最粗的能表示它的那一轮"。
听起来合理，但示教数据占了 batch 的一半，而**最光滑的示教轨迹自然归到最粗的轮次**。
于是第 0 轮的头拿到的全是最好画的轨迹，最深的头拿到的是谁都画不好的残渣。
**它是按"这条轨迹好不好画"在分头，不是按"执行质量"在分头**——所以粗的反而分高。
而且任务成绩掉到 0.00（同帧数下对照组已经 1.00）。

**第三种（`online_minimal`）为什么对**：关键是意识到**两类样本必须区别对待**：

- **在线 rollout 有"实际执行深度"**，而且 `minimal` 规则能精确恢复它——被强制到深度 r 的
  rollout 存下来的就是第 r 轮草图，探索噪声（σ=0.01）远小于容差（0.05）。
- **示教数据根本没有执行深度**——策略从来没执行过它们。一条示教就是一条全分辨率轨迹，
  只该给最深的头打标签。

第二种错就错在示教占大头，按"可表示性"归属它们等于按平滑度排序。
改完之后，示教给粗头的标签数 **16 → 0**（测试里量的）。

**三个种子都复现**，而且 `Δ`（相邻深度的价值差）**全部为正**——这正是规则要"说继续"所需要的：

```
N   Δ = +0.0786  +0.0449  +0.0098  +0.0330
N2  Δ = +0.0800  +0.0576  +0.0160  +0.0302
N3  Δ = +0.0499  +0.0386  +0.0099  +0.0242
```

**但先别庆祝。** 粗头现在只拿到 **0.2%–1.1%** 的 batch（`exec_n = [0.004, 0.006, 0.009,
0.011, 0.970]`），因为它们只能靠 ε 强制的在线 rollout 喂。样本这么少，
**现在这个"递增"有可能只是"粗头还没训起来、被共享主干拖着走"的假象，而不是真的量出了差异**。
判定方法：等粗头攒够数据后，这个顺序还在不在。

我已经据此又改了一版：损失函数原来是把所有深度**混在一起**算平均，于是拥有 97% 标签的
最深头独占了大约 100:1 的梯度。改成**每个深度各自归一化再平均**（`exec_loss_norm=per_depth`），
arm R / R2 / Rfast 正在跑。

### 3.3 那个 0% 的 baseline，不是算法的问题

这条最实际，价值也最高。

你有一个跑满 100,890 帧、40 次评测**全是 0.0** 的 CQN-AS run。原来的怀疑是"某个纪元参数
配错了"。关卡 1 用直接实验给了确定答案，而且答案比猜的更糟：

> **在生产配置下，把示教数据原样重放，成功率是 0/60。**

也就是说，**这个环境连自己的示教数据都跑不通**。两个各自独立、且各自足够致命的原因：

**原因 A：成功判据在数学上就不可能满足。**
`success_hold_seconds=1.0` 要求"成功状态连续保持 1 秒"，换算成 **50 个连续控制步**。
但示教数据在第一次达成目标之后，平均只多录了 **20.3 步**，最长 **26 步**，还有 9 条一步都没有。
**60 条示教，没有一条够长。** 只把这一项改成 0，成功率立刻从 0.000 变成 0.750。

打个比方：考试要求"连续站稳 1 秒"，但标准答案本身最多只站了半秒——满分答卷也不及格。

**原因 B：HOMIE 下半身控制器一开始就站错位置。**
它在 reset 那一刻、还没执行任何动作时，骨盆就已经偏离示教 **4.7 厘米**，到轨迹结束偏
**20 厘米**（对比：运动学浮动底座只偏 1.3 厘米）。单这一项就把 0.750 打到 0.017。

完整的定位表（每格 60 条示教）：

| 配置 | 重放成功率 |
|---|---|
| **生产配置**（hold=1.0, z=0.92）| **0.000** |
| hold=0, z=0.92 | 0.017 |
| hold=1.0, z=1.00 | 0.000 |
| hold=0, z=1.00 | 0.000 |
| hold=0, warmup=0 | 0.067 |
| hold=0, cmd_clip=5 | 0.100 |
| **浮动底座（示教录制时的配置）, hold=0** | **0.750** |

**这意味着**：这个仓库里所有 HOMIE 纪元的数字——包括那个 100K 帧的 baseline——
一直在测一个**谁都不可能得分的任务**。这不是算法结论，是环境配置结论。

顺带，关卡 1 本身的问题（粗草图还能不能完成任务）**通过了**：3 个点的草图达到 16 个点的
**109%**（0.817 vs 0.750）。所以"随时停笔"这个想法在物理上是站得住的。

| 草图点数 | 2 | 3 | 5 | 9 | 16 |
|---|---|---|---|---|---|
| 成功率 | 0.467 | **0.817** | 0.767 | 0.733 | 0.750 |

### 3.4 ZoomQ 目前没有比基线好

arm G 在 `drawer_top_close` 上把 reward 打到 **1.00** 并稳定住（7 次评测），
轨迹长度从 300 步的超时降到 133–164 步——它真的完成任务并提前结束。

但对照组 arm K（原版 CQN-AS，同任务同执行制度）：

| arm | 2.5K 帧 | 5.1K 帧 |
|---|---|---|
| G（ZoomQ）| **0.00** | 1.00 |
| K（CQN-AS）| **0.70** | 1.00 |

**K 在第一次评测就领先。** 所以诚实的说法是：ZoomQ 能训、能解任务，
**但没有任何证据说明它更好**。而且要注意，由于 §3.1，这些 arm 测的其实是
"停止规则被废掉的 ZoomQ"。

现在 G/K/N 三种子（G2/G3、K2/K3、N2/N3）都在并行跑，约两小时后会有 n=3 的版本。

### 3.5 论文说的"顺序决策链"，只实现了一半

论文 §3.2 用"顺序链"来论证 ZoomQ 的好处：后决定的点能看到先决定的点，所以能表达
"两个点必须配合"这种关系，而各自独立取最大值的做法做不到。

实测下来，信息其实有**两条**通道可以传：

1. **残差窗口的锚点**——窗口是围绕已确定邻居的连线画的，所以锚点本身就携带了信息；
2. **GRU 的循环**——但它每个位置的输入是"该位置自己的区间中点"。

在最粗的那一层，第 2 条通道**传递的信息量恰好是 0.000e+00**（实测，不是约等于）。
因为在最粗一层，每个位置的中点就是它自己窗口的正中心，跟别人选了什么无关。

所以：**ZoomQ 相对原版的协调能力提升是真的，但来自"带锚点的窗口"（§3.1 的机制），
不是来自那个序列模型。** §3.2 的说法夸大了 GRU 的作用。

我把锚点这条通道**故意堵死**（构造成两种模式下锚点都为 0）再测：

| 条件 | 结果 |
|---|---|
| 锚点开着 | bin 4 ↔ bin 0，**最大幅度翻转**——§3.1 的机制确实管用 |
| 锚点堵死，默认模式 | **0.000e+00**，循环什么都没传 |
| 锚点堵死，`cond_mode=final` | **2.523e-03**，通道打开了 |

修复已实现（把更早轮次按**最终确定值**重新喂一遍，代价约 2 倍循环计算量），
作为 arm D3 和 arm P 在跑。

顺带一个细节：**同一轮内的两个点也无法协调**——包括第 0 轮同时定的首尾两点。
这跟原版 CQN-AS 一样。要修的话得把第 0 轮拆成两轮。

### 3.6 论文给的窗口宽度全都太窄，因为有一个二值夹爪

关卡 0 在 7,709 个真实示教片段上量了每一轮的残差：

| 轮次 | 论文给的 w | 实测 `1.5 × p99` | 差距 |
|---|---|---|---|
| 1 | 0.15 | **0.5794** | 3.86× |
| 2 | 0.08 | **0.1624** | 2.03× |
| 3 | 0.04 | **0.0596** | 1.49× |
| 4 | 0.02 | **0.0395** | 1.97× |

**根因**：动作的第 13 维是**二值夹爪**，只有 `-1` 和 `+1` 两个值（其他每维都有 8000+ 个
不同取值）。当它在一个 chunk 内翻转时（12.53% 的片段会），线性插值它的残差可以到 **1.0667**
——**比整个动作范围还大**，任何窗口都装不下。

而且线性插值一个二值量在物理上是**没有意义的**：它会在两点之间的每一步都命令一个
"半开的夹爪"，这是示教数据里根本不存在的动作。

所以我加了**逐维度的窗口**和**逐维度的填充规则**（二值维用"保持"而不是"插值"）。

`j*`（需要几个点）实测是 **3**，不是论文说的 4——而且 4 根本不在这个二分调度的点数序列里
（序列是 2, 3, 5, 9, 16）。

**还有一个必须记的**：`drawer_top_close` 的动作是 **16 维**，不是 `move_plate` 的 15 维，
而且有**两个**死维、**没有二值夹爪维**。所以关卡 0 必须**逐任务重跑**，
`hold_dims=[13]` 是 `move_plate` 专用的。好在标定配置会因维度不匹配直接报错拒绝加载——
这个保护起作用了。

## 4. 工程上踩的坑（对以后有用）

- **上游 main 比 ali 上的 bigym 新**：训练脚本调用了一个 ali 的 bigym 没有的参数
  （`episode_seed_rng`），每条 arm 都在建环境时崩。修法是一个兼容层：**只在参数值为 None
  时才丢弃它，否则直接报错**——绝不能静默丢掉一个有值的参数。
- **`envsetup.sh` 返回非零**：脚本里有 `set -e` 的话会在 source 那一行直接退出，
  **日志是零字节，没有任何线索**。
- **评测比训练还费时间**：`eval_every_frames=2500` + 10 条评测轨迹，而这个任务的轨迹永远
  跑满 300 步超时，于是一次评测要 3000 步。实测占空比是 **训练 42 分钟 / 评测 50 分钟**
  ——**54% 的机时在产出关卡 1 已经证明毫无信息量的 0.0000**。我把只需要计数器的 arm 改成
  几乎不评测后，吞吐直接翻倍。
- **快照会把整个模块 pickle 下来**：我后加的 buffer 在旧快照里不存在，于是所有从旧快照
  恢复的 arm 全部在 `act()` 里挂掉。修法是在反序列化时重建这些 buffer（它们都是调度的
  纯函数，没有学到的东西，所以重建是精确的）。**以后再给 critic 加 buffer 都要走这里。**
- **CSV 表头在第一次写入时就定死**：所以所有计数器必须从第 1 步就全部输出，值为 0 也要输出。

## 5. 现在在跑什么

**26 条 arm，67 核 / 184 核。** 关键的几条：

| arm | 是什么 | 看什么 |
|---|---|---|
| G / G2 / G3 | ZoomQ，原始归属规则，3 种子 | 对照 |
| K / K2 / K3 | 原版 CQN-AS，3 种子 | 基线 |
| M | 修法 2（`minimal`）| 已否定，留作负对照 |
| N / N2 / N3 / Nfast | 修法 3（`online_minimal`），3 种子 + 1 条免评测快读 | **方向对了，但粗头缺数据** |
| R / R2 / Rfast | 修法 3 + 逐深度归一化损失 | **喂饱粗头之后顺序还在不在** |
| P | `cond_mode=final` 在有信号的任务上 | §3.5 的修复第一次真正被测 |
| A–F, D2/D3, H, I/I2, J | `move_plate` 各配置 | 机制计数器（任务本身无法得分）|

**大概什么时候有结果**：机制答案（顺序对不对、稳不稳）约 1 小时；
三种子的任务成绩对比约 2 小时。单条 run 的上限是 ~1 帧/秒（串行 env step），
所以并行只能让多个种子同时跑完，**没法让单条跑更快**。

## 6. 接下来该做什么（按价值排序）

1. **把整个研究挪到示教能跑通的配置上。** §3.3 已经不是猜测了。要么修
   `success_hold_seconds` **并且**修 HOMIE 骨盆跟踪，要么直接用浮动底座。
   **这件事没做完，别的都不重要**——现在所有 HOMIE 纪元的数字都在测一个没法得分的任务。
2. **盯 arm R 系列。** 如果逐深度归一化之后，`exec_q` 依然随深度递增，那 §3.1 就修好了，
   停止规则第一次有可能真的触发。如果粗头还是太饿，就把"实际执行深度"作为一个 `int8` 字段
   存进 replay buffer——那是最稳的版本。
3. **在下任何"ZoomQ 更好"的结论之前，先把对照跑够。** 目前 arm K 是**领先**的。
   n=1 种子、2 个评测点、最简单的任务——现在最多只能说打平。
4. **给夹爪一个离散头。** 二值维度用连续残差窗口去细化本身就没意义。
5. **重算论文 §4 的标定数字。** 窗口宽度四个轮次全对不上，`j*` 是 3 不是 4，
   而且要逐任务重算。
